# 演员与跨局记忆 —— 让「上局被谁骗过」活下来

> 2026-10-05。对应设计方案 §3.4 第 3 条（跨局记忆）与 §2.2 的第二层人设（玩家性格）。

## 0. 一句话

**跨局的连续性只能靠落盘的档案**——teammate 是会话内的成员，一局打完就散；而「一局一个会话」
拍板之后，这条路再没有第二个地方可放。

## 1. 为什么它从「锦上添花」变成了必须

`spawn_teammate` 建出来的玩家挂在一个 Team 上，而 Team 属于**那一局的会话**。会话一结束，
玩家连同它这一局学到的任何东西一起消失。

在此之前，这条缺口还能靠"反正都在同一个会话里"糊过去：同一会话连开两局，teammate 名册还在，
上下文也还在。但名册的上限（8 位，且条目不可移除）让连开两局本身就走不通——于是
**一局一换会话**成了约定，而那条糊法也就彻底没有了。

**这是设计方案的 §2.2 第二次被推到台前**：它把人设分两层，第一层是角色人设（本子给的），
第二层是**玩家性格**（这个人怎么玩游戏）——"同一份剧本换个人玩，玩法完全不同"。第二层要
成立，就需要一个不随会话消失的载体。

## 2. 判据一：演员 ≠ 座位

演员是**跨局存在的那个人**，座位是**这一局他坐哪儿**。两者刻意分开：

| | 属于谁 | 换一局还在吗 |
|---|---|---|
| 角色本 | 本子 | 不在了（换本子就换人） |
| 座位（p1 / p2） | 这一局 | 不在了（同一个人下局可能坐别处） |
| **演员** | 那个人 | **在** |

所以档案里记的是「上一局被人连珠追问逼出过话」这种，而不是「上一局我演林小满的时候……」。
**座位号进不了档案**，理由在 §4。

## 3. 判据二：落盘走宿主的 storage，不自己写文件

演员池用 `ctx.storage` 的域（`@deepseek-ai/dsh-storage-domain`）+ json 后端，与 `dsh-memory`
的 `memory.json` 同一个根目录：

```
$DSH_HOME/storages/jubensha.json
```

**为什么不自己 `writeFileSync`**：域有 zod schema 校验，**一条不合格的记录会让整个打开失败**
（`invalid-record`，fail loud）；手写的 JSON 坏掉时是静默半坏——少一条、多一个 `undefined`，
读的地方照样跑，只是数据不对。而这份数据是**跨局**的：坏一次会跟着之后每一局。

**为什么放 `$DSH_HOME` 而不是 `<cwd>/.dsh/storages`**：那个根随 git 分享，而演员池是私人的。
更要紧的是它**该跟着人走，不跟着工作区走**——换个目录开一局，坐下来的还是同一批人。

## 4. 判据三：上台说明里那段不写座位

演员那一段告诉玩家三件事：**谁在演**、**他怎么玩**、**他记得什么**。它不写座位号，因为
同一批演员换位子是常事——写了反而像在说"你换人了"。

顺序也是判据：演员段排在**角色本之前**。先知道"谁在玩"，再看他"这次演谁"。

印象只带**最近三条**进上台说明（`NOTES_IN_BRIEF`）。上限不是省事：印象在池子里会一直长，
而 brief 每局都要重发一遍——三条够他认出"上次栽在谁手里"，多出来的只会把角色本挤到后面。

## 5. 实测

隔离实例 + 会话日志，驱动脚本 `jubensha-drive.mjs` 的 step 11 / 12。

### 5.1 第一次跑：五个动作全挂

`jubensha_actor` 的 `add` / `note` / `list` / `show` **五个调用全部**返回：

```
Error: cannot get property "storage" without inject
```

**根因**：演员池要 `new DomainFacility(ctx, …)`，而它内部是按**属性**访问 `ctx.storage` 的——
属性代理只认**声明过的注入**。`actor.ts` 里写的是 `ctx.get('storage')`（那也是 DSH 的正规写法），
但那只解决「我自己怎么读这个服务」，解决不了「**我交给别人的那个 ctx 怎么读**」。

**连带伤害更值得记**：给 `spawn` 传 `actor` 会触发同一个错，**把整次上桌一起拖失败**；同一个
会话里不传 `actor` 的 `spawn` 一直正常。所以那个错看起来像「演员功能坏了」，实际是「插件没声明
自己依赖的服务」。

**修法**：`export const inject = ['tools', 'storage']`。

### 5.2 修好之后

| 判据 | 结果 | seq |
|---|---|---|
| 建两个演员 | 两次 `add` 都成 | 1204 / 1206 |
| 记一条印象 | `note` 成 | 1212 |
| 列池子 | `amay 阿May｜印象 0 条`、`laozhou 老周｜印象 1 条` | 1218 |
| 看档案 | 名字 + 风格 + 那条印象 | 1224 |
| **落盘** | `$DSH_HOME/storages/jubensha.json`，657 字节，unit 结构 | — |
| **跨进程** | **重启之后 `list` 仍然是** `laozhou 老周｜印象 1 条` | **1276** |

**最后一条才是这一块存在的理由**：同一个进程里列得出来不算数，重启之后还在才算。

### 5.3 没验到的：带演员上桌

`spawn` 传了 `actor` 的那一次报的是 `Team member limit 8 reached`——**不是** storage 错。
这说明演员那一段已经走通、卡在后面那个已知的名册上限（见
[`2026-10-05-桌面与信道.md`](2026-10-05-桌面与信道.md) §5.3）。所以「演员真的坐上了桌、
拿到了带跨局印象的上台说明」这件事**还只有间接证据**，要等一个新会话来验。

### 5.4 探针的一个局限

`jubensha-drive.mjs` 用「消息锚点数量变化」判断模型是否动过，而**重启后的新会话**里那个
计数与刚发的消息对不上——`step 12` 因此报了「锚点始终没变」，但工具调用其实发生了
（日志里 seq 1275/1276 俱在）。**界面锚点不是可靠判据时，会话日志才是。**
